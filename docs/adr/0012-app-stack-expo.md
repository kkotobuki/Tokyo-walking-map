# ADR-0012: アプリのスタック＝Expo、データは Notion を直接読み書き

- ステータス: Accepted
- 日付: 2026-06-21

## コンテキスト

コンセプト・データ・語彙が固まり（ADR-0001〜0011）、次は「賭け→答え合わせ→上達」のループが本当に面白いかを実機で確かめる段階に入った（product-brief.md）。スタックは長く「未確定」だったが、ユーザーが **散歩中に使うモバイルアプリ** として作ると明言した。

## 決定

1. **スタック＝Expo（React Native / TypeScript）**。ターゲットは **iPhone**（実機確認は Expo Go）。
2. **データは Notion を唯一の家として直接読み書き**する。アプリは既存DB「東京100駅経済観察マップ」(data source `e066cd64-d94f-44f1-acc5-e284ca84eec3`) を読み、ユーザーの記録（仮説・感想・訪問状態）を同じ Notion に書き戻す。
3. **オフライン耐性**を持たせる: 読みは起動時取得＋端末キャッシュ（圏外は直近を表示）、書きは圏外なら端末に貯めてオンライン復帰時に同期。
4. 認証は **Notion インテグレーショントークンをアプリが保持**する。`.env`/SecureStore で管理し、**コミットしない・コードに直書きしない**（CLAUDE.md 準拠）。

## 根拠

- **モバイルが用途そのもの**: 散歩・電車移動で使う（product-brief.md）。Web ではなく端末アプリが要る。Expo は iPhone 実機確認が Expo Go だけで完結し、立ち上がりが速い。
- **Notion 直読み書きで一貫**: ユーザーは自分一人（個人専用）。結果も自分の Notion に貯めたい以上、読みも Notion に寄せるとデータの家が1つで済む。静的JSON同梱より「いつ編集しても即反映」で、執筆（ローカルJSON→import）と閲覧が分離しない。
- **トークン同梱が成立する理由**: 配布しない個人アプリで、自分の端末でのみ動かすため。インテグレーションは当該ワークスペースに限定。将来配布するなら間にバックエンド（プロキシ）を挟む、と別途判断する。
- **オフライン必須**: 「行きの電車でクイズ」は地下鉄・トンネルで圏外になりうる。純粋な毎回フェッチでは成立しないため、読みキャッシュと書きキューを最初から設計に含める。

## 結果

- (+) 実機で最速にループの面白さを検証できる。
- (+) データの家が Notion 1つに揃い、執筆・閲覧・記録が同じ場所。
- (−) トークンを端末が持つため、配布時には設計変更（バックエンド）が必要。個人利用の範囲に閉じる前提。
- (−) Notion API はレスポンスが速くなく、オフライン同期の実装コストが乗る（MVPでは読みキャッシュ優先、書きキューは段階的に堅くする）。

## 検討した代替案

- **静的JSON同梱（ビルド時に Notion→JSON エクスポート）**: 読みは速く堅いが、結果を Notion に書き戻す以上どのみち Notion 通信が要り、「執筆した内容が即反映されない」分離が生まれる。個人専用なら直読み書きの方が素直なため却下。
- **Next.js などの Web**: 散歩中のモバイル用途に合わない。却下。
- **バックエンドを挟む（Supabase 等）**: 配布や多ユーザーなら妥当だが、個人専用の今は過剰。将来配布時に再検討。
