# ADR-0005: 街のコンテンツは生成せず「本文＋フラットタグ」で溜める

- ステータス: Accepted
- 日付: 2026-06-18

## コンテキスト

ADR-0002 で L3 を「**生成**ルール（アンカー × ショック × 地価／区画）」と呼んだ。
この「生成」は本来「**現実世界の力（大学があった・EC が来た）が街の形を生成した**」という意味だったが、「**アプリが街の説明文をアルゴリズムで生成する**」と読めてしまう言葉だった。

実際に DB の箱を設計しようとすると、この読み違いが効いてくる。「街の話は生成するのか、溜めるのか」「タグ（アンカー／ショック）にどこまで情報を背負わせるか（タグの粒度）」が決まらないと、テーブルの形が決まらない。

タグの粒度については2案あった。

- A案: フラットなタグ（`秋葉原 → [戦災+闇市][EC化]`、貼るだけ）
- B案: 属性つきの関係（`秋葉原 ×[EC化]{時期, 効果, 順序}`）

ADR-0003（需給の「ズレ」＝時間差を読む）/ ADR-0004（ショックの履歴・順序）を真に受けると B案に寄るが、そうするとタグが重くなる。

## 決定

1. **街の発展史・現在の様子は、人が文章（本文）として書いて溜める。生成しない。**
2. **本文は1駅あたり3000字以内**を上限の目安とする。
3. アンカー／ショック／類型は、その本文に貼る**フラットタグ**とする（タグ自体に時期・効果・順序などの属性を持たせない）。
4. 因果の詳細（いつ・どう効いたか）の richness は、すべて**本文**が持つ。タグは「横断で絞り込む／集計する」専用とする。
5. ADR-0002 の L3「生成ルール」は、以後「**駅に貼る分類タグの語彙（分類軸）**」と読み替える。L3 はメカニズムを**圧縮して指すラベル**であって、文章の生成器ではない。

## 根拠

- richness を本文が持つなら、タグは横断クエリのキー（例: `アンカー=大学` の駅を全部引く）に徹してよく、**フラット（A案）で十分**。これでタグの粒度問題が一気に軽くなる。
- B案（属性つき関係）は、本文と同じ情報（時期・効果）を二重に構造化することになり、執筆・保守の重複が大きい。ズレや順序は本文側で語れる。
- アプリ生成案は、ADR-0001 の「史実で答え合わせする」検証性と矛盾する。生成文は史実としての信頼性を担保できず、「答え」になれない。

## 結果

- (+) タグ設計が軽い。アンカー／ショック／類型のマスタを小さく保てる。
- (+) 横断パターン（ADR-0002 の狙い）はタグの集計・絞り込みで出せる。
- (+) 本文に自由度があり、ズレ・順序・例外を自然文で書ける。
- (−) 本文の執筆コストがかかる（全駅3000字を誰がどう書くかは未決＝史実データソースの論点）。
- (−) タグと本文の二重管理（本文の内容とタグがズレないよう運用が要る）。

## 検討した代替案

- **B案: 属性つきの関係（shock × 時期 × 効果）**: 本文と情報が重複し過剰。ズレ・順序は本文で語れるため却下。
- **アプリによる文章生成**: 検証性（ADR-0001）と史実の信頼性を担保できず却下。

## 暗黙の前提

- 「3000字以内」の根拠: 読み手で2〜3分、書き手にも現実的なサイズだから。厳密な制約ではなく目安。
- タグをフラットにできるのは、richness を本文が肩代わりするという前提が成り立つ場合に限る。本文を持たない運用に変えるなら、この前提ごと再検討が要る。
