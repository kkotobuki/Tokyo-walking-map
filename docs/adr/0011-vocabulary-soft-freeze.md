# ADR-0011: 語彙はボトムアップで立ち上げ、安定後はソフトフリーズ

- ステータス: Accepted
- 日付: 2026-06-21

## コンテキスト

「類型（およびアンカー/ショック/需要/ズレ類型）の語彙をどう作るか」は、**スキーマ先行**（歩く前に型を設計して固定）か **ボトムアップ**（何駅か変数化してから型を立ち上げる）かが未決のまま残っていた（NEXT_STEPS 0章）。

実態としては既に決着している：

- ADR-0005 で「タグはフラット・語彙はボトムアップで増やしてよい」と方針化した。
- 秋葉原のパイロットから 111 駅までの変数化は、サブエージェントの提案を拾って語彙を育てる**ボトムアップ運用で最後まで回り切った**。`data/vocab.ts` を単一ソースに、`pnpm run import` が未知タグを警告で surface する仕組みも定着した。
- 一方で副作用として類型が 15 種まで発散し、**ADR-0010 で 11 種に刈り込んだ**。「足し放題」は型の意味を薄め、産業名を型と需要で二重に持つ冗長を生む。

つまり論点は「スキーマ先行 vs ボトムアップ」ではなく、**ボトムアップで立ち上げた後の“足し方のガバナンス”**に移っている。

## 決定

語彙のライフサイクルを2段階で運用する。

1. **立ち上げ期＝ボトムアップ**（実施済み・完了）: 実駅を変数化しながら必要な語彙を下から足す。111 駅で一巡し、この期は終えた。
2. **安定期＝ソフトフリーズ**（ここから）: 語彙は原則固定。**新タグの追加には「既存語彙では書けない」ことの提示と、ADR への理由記載をゲートとして課す**。

ソフトフリーズの運用ルール：

- 新タグが欲しくなったら、まず**既存タグ＋本文で表現できないか**を試す。表現できるなら足さない。
- 本当に既存語彙で表せない駅に出会ったときだけ、**新しい ADR（または既存 ADR への追記）に「なぜ既存で書けないか」を残して**から `data/vocab.ts` に足す。
- `data/stations/*.json` の `proposedNewOptions` は「足す前のバックログ」であり、追加の予約ではない。実駅で必要性が確認できた時に上記ゲートを通す。
- 追加したら `data/vocab.ts`（単一ソース）→ Notion スキーマ → `docs/station.ts`（vocab から型 import 済みなので追従不要）→ 必要なら `docs/patterns.md` の順で反映する。

## 根拠

- **発散の再発防止**: 「自由に足す」は ADR-0010 で刈り込んだばかりの 15 種問題を再来させる。ADR ゲートはその逆流を止める。
- **完全フリーズより柔軟**: 東京 111 駅で主要語彙は出尽くした感触があるが、未踏の街型がゼロとは言い切れない。完全固定だと未知に出会ったとき本文へ逃がすしかなく、横断クエリ（タグ）に乗らない。ソフトフリーズなら「理由つきで足せる」余地を残せる。
- **既に踏んだ流れの正典化**: 「ボトムアップで立ち上げ → 安定したら ADR ゲート」は、まさに ADR-0005→0010→本ADR で実際に歩いた道。运用を後付けで腐らせず明文化する。

## 結果

- (+) 語彙の追加に必ず理由（Why）が残り、型の意味が保たれる。
- (+) `proposedNewOptions` の扱いが「バックログ（要 ADR 判断）」と明確になり、import 警告のノイズも判断待ちの語彙だけに絞られる。
- (−) 新タグ追加の手間が増える（ADR を書く）。ただし頻度は低い想定で、むしろ抑止が目的。
- これにより NEXT_STEPS 0章の「類型の作り方」論点は解消する。

## 検討した代替案

- **A. ボトムアップ継続（自由に足す）**: 立ち上げ期には機能したが、ADR-0010 で刈ったばかりの発散を再発させるため安定期には不適。却下。
- **C. 完全フリーズ**: 発散は確実に止まるが、未知の街型に出会ったときタグに乗せられず横断分析の網から漏れる。柔軟性を欠くため却下。
