# ADR-0008: 保存先は Notion 先行（既存「東京100駅経済観察マップ」DBを再利用）

- ステータス: Accepted
- 日付: 2026-06-18

## コンテキスト

保存先／スタックは未決だった（Notion先行 / Next.js + Supabase / ローカルの3案、ADR-0003 はDB設計の思想であって技術選定ではない）。

調べると、Notion に既存DB **「東京100駅経済観察マップ」**（親: 東京経済観察プロジェクト 2026 → 自己理解データベース、data source `collection://e066cd64-d94f-44f1-acc5-e284ca84eec3`）があり、50〜100駅が**観光寄りのプロパティ（おすすめルート・予算上限・カテゴリ・観察ポイント等）＋本文は空**の状態で入っていた。

まずは「基本データ＝本文＋タグ」を溜める運用を、コードを書かずに回したい。

## 決定

1. **スタックは Notion 先行**とする。アプリ実装（Next.js + Supabase 等）は、運用で語彙・骨格の型が固まってから別ADRで判断する。
2. **新規DBは作らず、既存DB「東京100駅経済観察マップ」を再利用**する。
3. タグは **multi-select プロパティ**として追加する: `アンカー` / `ショック` / `需要` / `類型` / `ズレ類型`（ADR-0002, 0005）。`路線` も multi-select で追加。
4. **本文の各パートも個別プロパティ（rich_text）＝変数として持つ**: `観察お題`(①の問い) / `お題の解説`(①の問いへの直接の答え) / `供給の筋`(③) / `需要の筋`(③) / `ズレ`(④) / `未来の観点`(⑤)。Notion ページ本体には**作り込まない**（ページ本文は「データは変数にある」旨の注記のみ）。
   - `当たり外れ` は**持たない**（不要と判断）。ユーザーの仮説入力もアプリ側。
5. **ループUI（観察→賭け→めくる→メモ）・ユーザーの仮説・歩行メモ（時系列）はアプリ側で実装**する。Notion は「アプリが API で取り出す変数の置き場」であって、デザイン／UXの場ではない。
6. 既存の観光寄りプロパティ（予算上限・住みたさ・儲かりそう度・面白さ・おすすめルート・観察ポイント・カテゴリ）は当面**残置**。整理は将来。

## 根拠

- 「縦に薄く1駅をエンドツーエンド」（CLAUDE.md）を**即**検証できる。実際に秋葉原で本文（各パート変数）＋タグを通し、語彙・骨格が破綻しないことをコード無しで確認した。
- 既存の50〜100駅という資産を捨てずに活かせる。
- 本文をパートごとの個別プロパティに分けることで、**アプリが Notion API で変数として素直に取り出せる**（ページ本文をパースするより堅牢）。multi-select＝フラットタグ（ADR-0005）もそのまま変数になる。
- Postgres ライクな構造（プロパティ＝列、ページ＝行）なので、将来アプリ化（Next.js + Supabase 等）する際の移行余地が残る。

## 結果

- (+) 即運用・低コストで、語彙／骨格の検証サイクルが速い。
- (+) 既存駅データを活かせる。各パートが変数なので、アプリは Notion を**バックエンド（CMS）**として読むだけで描画できる。
- (+) ループUI（観察→賭け→めくる）の体験設計は、Notion の制約に縛られずアプリ側で自由に作れる。
- (−) 将来アプリ化時に移行作業が要る（ただし構造は移行しやすい）。
- (−) 観光寄りの旧プロパティが混在し、スキーマが当面ノイジー。

## 検討した代替案

- **最初から Next.js + Supabase**: 語彙・骨格の型が固まる前の実装は手戻りが大きい。型が固まってからでよい。
- **ローカル（Markdown / SQLite）**: Notion の既存資産と、トグル／multi-select という既製UIを捨てることになる。

## 補足

- 親データベースの表示名は「東京50駅経済観察マップ」、データソース名は「東京100駅経済観察マップ」と不一致があるが、実体は同一DB（`collection://e066cd64-d94f-44f1-acc5-e284ca84eec3`）。
