# ADR-0018: 出発前プラン（定番スポット＋長さ2段のコース）を事前開示する

- ステータス: Accepted
- 日付: 2026-07-05
- 関連: ADR-0001（答えを隠す思考シミュレータ）の「隠すもの」の線引きを明確化。ADR-0005（本文＋フラットタグ）・ADR-0009（ローカルJSON先行＋一括投入）のデータの持ち方に従う。

## コンテキスト

くじ（🎲）で駅を選ぶ機能はあるが、出発前にアプリが見せるのは駅名・区・路線・観察お題のみ。「どこを・どれくらい歩くか」が分からないため、実際にはくじを引いた後にネットで観光地と所要時間を調べてから出発する必要があり、「サイコロを振って事前準備なく出発する」という体験が成立していない。

駅データには「おすすめルート」（順路テキスト）と「観察ポイント」があるが、

- 表示が現地フェーズ（onsite）からで、出発前には見えない。
- 内容が観察視点の順路（例:「柴又駅→帝釈天参道→帝釈天」）で、定番スポットの固有名詞の説明も所要時間も無く、「行っても困らない」水準に達していない。

背景には ADR-0001 の「答えを読む装置ではない」という思想があり、事前に見せる情報を意図的に絞ってきた。ただしユーザーの困りごとは「答えを知りたい」ではなく「準備の手間をなくしたい・行って困りたくない」であり、隠す対象の線引きを見直す必要がある。

## 決定

**「実用情報」と「解釈」を分け、実用情報は出発前に全部見せる。隠すのは解釈だけとする。**

- 実用情報＝どこを・どの順で・どれくらい歩くか（定番スポットの固有名詞を含む）。出発前（行きの電車＝outbound）から開示する。
- 解釈＝この街はなぜこうなったか（お題の解説・供給/需要の筋・ズレ・未来の観点）。従来どおり帰り（答え合わせ）まで隠す。
- 定番スポット名は街の性格のヒントにはなるが、現地に行けば必ず目に入る情報であり、隠しても答え合わせの価値を守れない。仮説ゲームが賭けているのは「スポットが何か」ではなく「なぜこの街がこうなったか」なので、事前開示してもゲームは壊れない。

### 新フィールド（Notion rich_text・任意3つ）

| プロパティ名 | 内容 | フォーマット |
| --- | --- | --- |
| 定番スポット | その駅の定番3〜5個 | 1行1スポット「名前 — 一言説明」 |
| さくっとコース | 30〜45分で駅前の定番を一周 | 「約◯分｜駅◯◯口→A→B→…→駅」 |
| しっかりコース | 90〜120分で名所を回りきる | 同上 |

- コースは長さ2段。実際の散歩は「今日は時間があるか・ないか」の二択で選ぶことが多く、3段以上はデータ量産コスト（全111駅×手書き）に見合わない。
- 所要時間はコース文字列の冒頭に埋め込む（「約40分｜…」）。専用の数値プロパティは作らない（ADR-0005 の「本文＋フラットタグ」に従い、構造化はしない。ソートや絞り込みに使いたくなった時に別ADRで判断）。
- データはローカルJSON（`data/stations/*.json`）に日本語キーで持ち、`pnpm run import` で Notion へ投入する（ADR-0009 のパイプラインをそのまま使う。任意フィールドなので空でも既存値を上書きしない）。

### 表示

- 駅ループ画面の outbound / onsite フェーズに「出発前プラン」ブロックを置き、定番スポット・2コース・既存の「おすすめルート」「観察ポイント」をまとめて表示する（おすすめルート・観察ポイントの表示開始を onsite から outbound に前倒し）。
- 帰り（return/done）の答え合わせ表示は変更しない。

### 既存「おすすめルート」との関係

- おすすめルートは「観察のための順路」（何を見ながら歩くか）、コースは「散歩プラン」（どこをどれくらい歩くか）として併存させる。重複が煩わしくなったら統合を別ADRで判断する。

## 根拠

- 「サイコロを振ってそのまま出発できる」には、出発前に(1)定番スポットの固有名詞 (2)歩く順路 (3)所要時間 の3点が揃っている必要がある。既存フィールドの表示前倒しだけでは(1)(3)が欠ける。
- 実用情報／解釈の線引きにより、ADR-0001 の中核（自分の仮説を残し史実で答え合わせする）を壊さずに準備ゼロ体験を足せる。

## 結果

- (+) くじ→プラン確認→出発が完結し、事前のネット調査が不要になる。
- (+) 観光地でない駅（住宅街など）も「困らないコース」を持てば、くじの当たり外れ感が減る。
- (−) 全111駅ぶんのスポット・コース・所要時間を書く量産コストが発生する。パイロット3駅（両国・柴又・学芸大学）で粒度と正確さを確認してから量産する。
- (−) 実在スポット・所要時間という「間違いがユーザーの実害になる」データが増える。量産時は不確かな情報をWeb検索で裏取りする。

## 検討した代替案

- **既存「おすすめルート」の表示前倒しのみ**: 実装は最小だが、定番スポットの説明と所要時間が無く「行っても困らない」に届かない。却下。
- **コース3段階（30分/60分/120分）**: 書き分けコストが約1.5倍になるわりに、選択は実質「時間があるか・ないか」の二択。まず2段で運用し、不足したら拡張。
- **外部API（Google Places 等）でスポット自動取得**: 量産コストは消えるがAPI費用と依存が増え、チェーン店等のノイズ除去が別途必要。街の文脈に沿ったキュレーションは本文と同じ手書き（AI下書き＋裏取り）の方が質が揃う。却下。
