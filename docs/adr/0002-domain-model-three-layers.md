# ADR-0002: ドメインモデルの3層構造（駅 / 類型 / 生成ルール）

- ステータス: Accepted
- 日付: 2026-06-16

> **補足（ADR-0005, 2026-06-18）**: 本ADRの L3「**生成**ルール」は、「現実の力が街を生成した」の意であって、アプリが文章を生成する意ではない。
> 実装上は「駅に貼る**分類タグの語彙（分類軸）**」として扱う。詳細は ADR-0005 を参照。

## コンテキスト

最終目的は「東京というシステムを理解する」こと。
だが「1駅 = 1ページ」の図鑑形式は、各駅を独立ノードとして並べるだけで、**駅と駅の関係やパターン** が見えてこない。システムはノード（個々の駅）ではなく、**エッジ（関係）と生成規則** に宿る。

また「類型（門前町型・大学集積型 など）」と「なぜ発達したか」を混同しがちだが、両者は別のレイヤー。類型は結果として出てくる圧縮ラベルであり、「なぜ」はその型を生み出す力（メカニズム）の方にある。

## 決定

ドメインを **3層** で構造化する。

- **L1 駅（個別）**: 神保町、秋葉原 … 観察・記録の単位。
- **L2 類型**: 門前町型・大学集積型・闇市あがり型 … L1を圧縮した中間語彙。
- **L3 生成ルール**: **アンカー × ショック × 地価／区画**。型を生み出すメカニズムの本体＝「なぜ」の正体。

「なぜ東京はこうなったのか」は L3 に宿る。L2 は L3 へ辿り着くための中間語彙（圧縮辞書）として扱う。

## 根拠

- 100駅を独立記事として書くのではなく、**小さな生成文法** に圧縮できる（薄い抽象＋生成ルール、という普段の設計嗜好に合致）。
- 各駅は語彙で「綴る」対象になる。例: 神保町 = アンカー[大学] × ショック[EC化]。
- 横断したときにメタパターン（例: 知識産業はこういう立地条件で固まる）が立ち上がる。

## 結果

- (+) 拡張容易。新しい駅も既存語彙の組み合わせで表現できる。
- (+) システム理解（横断パターン）が得られる。
- (−) 語彙（マスタ）の初期設計コストがかかる。
- (−) 類型の粒度設計が難しい（粗すぎると無意味、細かすぎると図鑑に逆戻り）。

## 検討した代替案

- **フラットな図鑑（駅ごと独立記事）**: 関係・パターンが見えず、システム理解に繋がらない。記述の重複も多い。
