# ADR-0017: 未収録駅は検索エイリアスで主体駅に吸収する

駅検索のカバレッジ設計を記録する。読者は、検索まわりを触る実装者と、駅データの追加基準を判断する者。

## 状況

収録駅は語彙・ズレ類型の検証価値で手選定しており（NEXT_STEPS の変数化ログ参照）、路線網羅ではない。そのため実在する駅名で検索してもヒットしない（例: 池尻大橋）。検索が空振りすると「データがないのか、検索が壊れているのか」を利用者が判別できない。

一方、未収録駅を本文付きの駅レコードとして追加するのは1駅あたり最大3000字の執筆コスト（ADR-0005）がかかり、検索ヒットのためだけに払うコストではない。

## 決定

- 未収録駅は、近隣の収録駅（主体駅）の「圏内」として合同で扱う。
- 対応表は2層のローカルTSデータで持つ。形式はどちらも「主体駅名 → 吸収する駅名の配列」。
  - **手作業層** `data/stationAliases.ts`: 土地勘で決めた割り当て。自動層より優先（手作業層にある駅名は自動生成の対象外）。
  - **自動生成層** `data/stationAliasesAuto.ts`: `scripts/build-station-aliases.ts`（`npm run build:aliases`）が生成。OSM Overpass から都内の全駅（railway=station / tram_stop）を取得し、`stationCoords.ts` の収録駅への直線距離で最寄り割り当てする。最寄りが4km超なら「圏内」と呼べないため割り当てない（青梅・八王子・町田方面が対象外になる）。最寄り距離の1.25倍以内の同着は最大3駅まで複数割り当てする（境界の駅は両方ヒットしてよい）。
- 検索（`src/HomeScreen.tsx`）は駅名で当たらない場合に2層を順に照合し、ヒット時は一覧に「◯◯はこの駅の圏内」と表示して、なぜその駅が出たかを利用者に示す。
- 照合は `src/coords.ts` の `normKey`（NFKC・空白除去・「駅」サフィックス除去・ヶ/ケ統一）で正規化して行う。
- 自動層への手修正はしない（再生成で消える）。割り当てを直したいときは手作業層に移して再生成する。手作業層の目安は隣駅〜徒歩1.5km圏。

## 理由

- 主体駅への合同は、このアプリの単位が「駅」ではなく「街（歩く範囲）」であることと整合する。池尻大橋を三軒茶屋圏として出すのは、コンテンツ上も自然な誘導になる。
- Notion のプロパティではなくローカルTSにしたのは、エイリアスが本文を持たない検索用メタデータであり、JSON → Notion 一括投入（ADR-0009）に乗せる価値がないため。Notion スキーマ変更・import スクリプト改修・全端末への反映待ちが不要になる。座標を `data/stationCoords.ts` にローカルで持つ前例とも揃う。

## 検討して却下した案

- **未収録駅を駅レコードとして追加する**: 検索ヒットが目的なら執筆コスト（ADR-0005 の3000字）が見合わない。書く価値がある駅は従来どおり変数化すればよく、本決定と排他ではない（変数化したらエイリアスから主体駅へ昇格させる）。
- **Notion に「別名」プロパティを追加する**: データの一元管理はできるが、スキーマ変更と import 改修が必要になり、本文を持たないメタデータのために ADR-0009 のフローを太らせる。エイリアスの編集頻度は低く、コード側のデータで十分。
- **路線・区名でのあいまい検索だけで済ます**: 「池尻大橋」というピンポイントの駅名入力には答えられず、空振り問題が解決しない。
- **手作業層だけで網羅する**: 都内の駅は600超あり、手作業では書き切れず腐る。距離ベースの機械割り当てで裾野を覆い、判断が要るところだけ手作業層に置く2層構成にした。
- **実行時に外部API（Overpass等）を叩く**: オフラインの散歩中に使うアプリなので、実行時依存は増やさない。生成結果をデータとしてコミットする（`stationCoords.ts` と同じ方式）。
