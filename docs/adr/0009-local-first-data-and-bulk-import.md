# ADR-0009: 駅データはローカル先行＋一括投入、語彙は単一ソース

- ステータス: Accepted
- 日付: 2026-06-19

## コンテキスト

駅をサブエージェント並列で増やす運用（ADR-0008 で Notion を保存先に確定）を回すうち、次の問題が出た。

1. **トークン効率**: タグ語彙を増やすたびに Notion の `ALTER`（データソース更新）を呼ぶと、応答に全スキーマ（全オプション）が返り、メインの会話に毎回数万トークン乗る。駅数に比例して悪化。
2. **語彙の一貫性**: 語彙が Notion 側にしか無く、都度 ALTER で増やすため、一貫性の管理が散らばる（「専門◯◯街型」乱立などの発散も招く）。
3. **責務の混在**: サブエージェントが Notion へ直接書くと、本文執筆と Notion API 操作（プロパティ整形・スキーマ制約対応）が混ざる。

## 決定

1. **駅データはローカル先行**: 1駅 = `data/stations/<駅名>.json`（`StationRecord` 形式・日本語キー＝Notion プロパティ名）に**先に書く**。これが真実の源。
2. **語彙は単一ソース**: `data/vocab.ts` に全タグ（アンカー/ショック/需要/類型/ズレ類型/路線/カテゴリ）を `as const` 配列で集約。型もここから導出。新語彙はまずここに足す。
3. **一括投入**: `scripts/import-stations.ts` が `data/stations/*.json` を読み、Notion DB へ **upsert**（駅名 title で照合、無ければ create）。multi_select は **Notion API が未知オプションを自動生成**するため、事前のスキーマ変更（ALTER）は不要。
4. **サブエージェントの責務を単純化**: サブエージェントは Notion を触らず**ローカル JSON を書くだけ**。`data/vocab.ts` の値のみ使い、足りなければ `proposedNewOptions` に記録。import が vocab 未登録タグと提案を警告として集計する。

ADR-0008（Notion を保存先とする）は維持。本ADRはその**オーサリング手順**を「直書き」から「ローカル先行＋一括投入」へ更新するもの。

## 根拠

- スキーマの巨大ダンプを会話に持ち込まなくなり、**メインのトークン消費が激減**。
- 語彙が1ファイルに集約され、**一貫性をコードで検査**できる（未登録タグを警告）。
- ファイルが真実なので**再投入・再現が容易**（冪等な upsert）。Git 差分でレビューもできる。
- サブエージェントの仕事が「調べて JSON を書く」に純化し、Notion API の制約から解放される。

## 結果

- (+) トークン効率・語彙一貫性・再現性が大きく改善。
- (+) 駅データが Git 管理下に入り、差分・レビュー・バックアップが効く。
- (−) Notion 直書きの即時性は失う（一括投入のひと手間）。
- (−) 初期設定（Notion 内部インテグレーション作成＋トークン＋`pnpm i`）が要る。
- (−) 既に Notion にある34駅は当面 Notion 側が真実（必要なら将来 export でローカル化）。

## 検討した代替案

- **MCP で1駅ずつ直書きを継続**: 実装は不要だが、駅数に比例してトークンが浪費され、語彙も散逸するため却下。
- **Notion を捨ててローカル(SQLite等)を主に**: ADR-0008 の既存資産・既製UIを捨てることになり、現段階では過剰。Notion を CMS として残す。

## 補足（初期設定）

1. Notion で内部インテグレーションを作成 → トークン取得 → 対象DB（東京100駅経済観察マップ）に「接続」。
2. `export NOTION_TOKEN=...`、`pnpm i`、`pnpm run import`（または `pnpm run import 渋谷 上野` で一部）。
